# 03. K3s 클러스터 구축

## 목표와 선택 이유

단일 Ubuntu VM에서 Kubernetes의 Deployment, Service, PVC, Secret, Ingress를 익힌다. K3s는 Kubernetes 배포판이며 Docker Compose의 기능을 자동 변환하는 도구가 아니다. 처음에는 control plane과 workload를 같은 노드에서 실행한다.

K3s는 기본 containerd를 사용한다. Docker에서 빌드한 이미지가 자동으로 K3s에 나타나지 않는다. Registry pull 또는 이미지 import를 명시적으로 수행해야 한다.

## 1. 설치 전 기록

- Ubuntu 버전, VM hostname, 고정 IP, vCPU·RAM·디스크
- 사용할 K3s 버전: `<K3S_VERSION>` — 공식 릴리스에서 선택 후 고정
- 기본 Pod/Service 네트워크가 집 LAN·회사 VPN 대역과 충돌하는지 확인
- 시간 동기화, DNS 해석, 인터넷 outbound HTTPS 확인
- 80/443 포트를 점유한 다른 웹 서버가 없는지 확인

```bash
hostnamectl
free -h
df -h
ip route
sudo ss -lntup
```

swap 정책은 선택한 Kubernetes/K3s 버전의 공식 요구 사항에 맞춘다. 초기에 swap 없이 고정 RAM으로 시작하는 구성을 우선 검토한다. swap을 끌 경우 메모리 부족 때 OOM이 더 직접적으로 발생하므로 RAM 예산을 확인한다. 실제 fstab 항목을 확인하지 않고 일괄 치환하지 않는다.

## 2. 단일 서버 설치

아래 placeholder를 실제 검증한 버전으로 바꾼다. 설치 스크립트도 읽은 뒤 실행한다.

```bash
curl -sfL https://get.k3s.io -o /tmp/install-k3s.sh
less /tmp/install-k3s.sh
sudo env INSTALL_K3S_VERSION='<K3S_VERSION>' sh /tmp/install-k3s.sh
sudo systemctl status k3s --no-pager
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get pods -A
```

모든 노드가 Ready인지, CoreDNS·Traefik·local-path provisioner가 정상인지 확인한다. 설치 버전에 따라 기본 리소스 이름은 다를 수 있다. 실패하면 `sudo journalctl -u k3s -n 150 --no-pager`를 확인한다.

## 3. kubectl 관리 설정

관리 사용자에서만 실행:

```bash
mkdir -p "$HOME/.kube"
sudo cp /etc/rancher/k3s/k3s.yaml "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"
chmod 600 "$HOME/.kube/config"
kubectl get nodes
kubectl get storageclass
```

kubeconfig는 클러스터 관리자 자격증명이다. 저장소·메신저·CI artifact에 올리지 않는다. 다른 컴퓨터에서 사용하려면 localhost server 주소 수정뿐 아니라 서버 인증서 SAN, 방화벽, 접근 경로를 함께 확인해야 한다. 초기에는 VM 안에서 관리한다. 6443은 인터넷에 포트 전달하지 않는다.

## 4. namespace와 저장소 구조

향후 실제 인프라 파일은 아래 구조로 추가한다. 이 단계 문서 작성만으로 해당 파일은 생기지 않는다.

```text
infra/
  k8s/
    base/                 # API 공통 Deployment·Service
    overlays/staging/     # 테스트 namespace·이미지·설정
    overlays/production/  # 운영 namespace·리소스
    database/             # StatefulSet·PVC·마이그레이션
    ingress/              # TLS·Ingress
    monitoring/           # 모니터링 values·규칙
  ci/                     # 빌드·배포 절차
```

```bash
kubectl create namespace seraph-staging
kubectl create namespace seraph-prod
kubectl get namespaces
```

이미 존재하면 create 오류는 재생성하라는 뜻이 아니다. 선언형 YAML로 관리할 때는 `kubectl apply`를 사용한다. 운영과 staging의 Secret·DB·PVC를 공유하지 않는다.

## 5. 스토리지 원칙

- 최초 실습은 K3s local-path StorageClass로 시작할 수 있다.
- local-path의 데이터는 해당 노드 VM 디스크에 있다. 노드가 사라지면 다른 노드가 같은 데이터를 자동 제공하지 않는다.
- PVC 이름·바인딩 PV·노드·실제 디스크 경로를 기록한다.
- StorageClass reclaimPolicy를 확인한다. Delete 정책에서 PVC를 지우면 실제 데이터도 삭제될 수 있다.
- StatefulSet replica 수를 올린다고 PostgreSQL 복제가 구성되지 않는다. DB는 일단 1개 replica다.
- Longhorn 같은 분산 스토리지는 별도 단계다. 같은 물리 SSD의 VM 복제는 물리 장애 대비가 아니다.

```bash
kubectl get storageclass -o yaml
kubectl get pvc -A
kubectl get pv
```

## 6. 방화벽과 네트워크

K3s 공식 요구 사항의 서버·agent 포트 및 선택한 CNI 요구 사항을 확인한다. 기본 Flannel VXLAN 사용 시 UDP 8472는 노드 간에만 필요하며 인터넷에 공개하지 않는다. API server TCP 6443, kubelet TCP 10250도 필요한 신뢰 노드·관리 경로에만 허용한다.

Docker/K3s가 만드는 iptables/nftables 규칙과 UFW 상호작용을 확인한다. 무작정 UFW를 켜고 SSH가 끊기지 않도록 VM 콘솔을 확보한다. LAN에서 허용할 포트와 WAN에서 허용할 포트를 따로 기록한다.

## 7. 이미지 전달

Registry 구축 전에는 맥북에서 그램의 linux/amd64용 이미지를 만들고 파일로 전달한다. MacBook의 Docker 런타임·Buildx 지원을 먼저 확인한다. 이후 Registry가 준비되면 07 문서의 push/pull로 전환한다.

**맥북 터미널, 저장소 루트:**

```bash
docker buildx build --platform linux/amd64 --load -t seraph-backend:lab-001 .
docker image inspect seraph-backend:lab-001 --format '{{.Os}}/{{.Architecture}}'
docker save -o /tmp/seraph-backend-lab-001.tar seraph-backend:lab-001
scp /tmp/seraph-backend-lab-001.tar <ADMIN_USER>@<SERVICE_VM_IP>:/tmp/
```

inspect 결과가 linux/amd64인지 확인한다. 빌드 context가 로컬 맥북인지 확인하고 원격 builder를 그램으로 지정하지 않는다.

**그램 Ubuntu VM, SSH 세션:**

```bash
sudo k3s ctr images import /tmp/seraph-backend-lab-001.tar
sudo k3s ctr images list
```

Deployment 태그와 `imagePullPolicy: IfNotPresent`를 맞춘다. 여러 노드라면 모든 스케줄 대상 노드에 import가 필요하다. 운영 전환 후 immutable tag/digest를 사용한다. 전송 archive는 정상 import 확인 후 정리하고 복구용 사본은 별도 보존한다.

공식 참고: [Docker 대상 플랫폼 빌드](https://docs.docker.com/build/building/multi-platform/).


## 8. 다중 노드 확장: 자원 증설·실측 후

현재 장비(RAM 16GB·저장 공간 여유 약 39GB)에서는 단일 VM이 초기 구성이다. 공간 확보·자원 실측 또는 증설 후 별도 실습으로 agent VM 추가를 검토한다. 서버는 1대, agent를 추가하는 구성은 control plane 고가용성이 아니다.

1. 별도 Ubuntu VM을 만들고 hostname·IP를 다르게 지정한다.
2. 동일한 K3s 버전과 서버 접근 경로를 확인한다.
3. 서버의 node-token을 안전하게 전달한다. 토큰을 로그·문서에 붙이지 않는다.
4. 공식 quick-start의 `K3S_URL`, `K3S_TOKEN`을 사용해 agent로 등록한다.
5. `kubectl get nodes -o wide`에서 Ready를 확인한다.
6. API를 여러 replica로 늘려 배치를 관찰한다. local-path DB는 원래 노드에 남긴다.
7. drain 실습은 백업 후 staging 노드에서만 한다. DB 노드를 무작정 drain하지 않는다.

## 9. 검증과 복구 연습

- 시스템 Pod가 정상이고 CoreDNS가 서비스 이름을 해석하는지 확인한다.
- 테스트 API Pod 삭제 후 Deployment가 다시 만드는지 확인한다.
- VM 재부팅 후 node Ready·PVC·API 복구를 확인한다.
- 이미지 없거나 Secret이 틀린 실패를 staging에서 만들어 describe/events로 진단한다.

문제 확인 명령:

```bash
kubectl get pods -A -o wide
kubectl get events -A --sort-by=.lastTimestamp
kubectl describe node <NODE_NAME>
sudo journalctl -u k3s -n 100 --no-pager
```
