# 06. 로컬 AI와 설명서 데이터

## 목표와 현재 한계

외부 AI API를 호출하지 않고 설명서 근거 검색을 수행한다. 현재 `/api/chat/ask`는 검색된 근거 중심 응답이며, 별도 생성 LLM이 완성된 챗봇은 아니다. 1차 목표는 로컬 임베딩 + PostgreSQL 키워드/벡터 하이브리드 검색이다. 자연어 답변 생성 LLM은 자원과 품질을 확인한 뒤 추가한다.

현재 코드 확인:

- `backend/src/embeddings.ts`: OpenAI SDK client, API key 필요, embeddings 요청에 dimensions 포함.
- `backend/src/env.ts`: OPENAI_* 설정만 있음. 로컬 endpoint/provider 선택 기능 없음.
- `db/migrations/009_manual_revisions_and_vector_search.sql`: vector(1024), 검색 함수·인덱스 포함.
- `backend/src/importers/embedManualChunks.ts`: 대기 청크를 임베딩하는 batch worker.
- 키가 없으면 API 검색은 키워드 경로로 동작할 수 있음.

따라서 로컬 모델 서버만 띄워도 현재 코드가 자동으로 사용하지 않는다. 이 문서는 필요한 구현 작업을 계획한다.

## 1. 확인한 장비와 모델 선택 범위

확인한 장비는 i5-1240P·RAM 16GB·Intel Iris Xe다. 화면의 128MB 표기만으로 GPU가 사용할 총 공유 메모리를 판단하지 않는다. GPU의 VM 전달 가능성·가속 지원은 미정이며, 초기에는 6GB RAM VM에서 CPU 추론으로 작은 임베딩 모델을 평가한다. 특정 대형 모델이나 GPU 전용 런타임을 확정하지 않는다. 작은 CPU 모델로 개념 검증하고 실제 한국어 품질·처리량을 측정한다. Windows의 GPU가 Linux VM에서 자동으로 사용되는 것은 아니다.

모델 후보 평가표:

| 항목 | 기록할 값 |
| --- | --- |
| 모델명·정확한 revision/hash | 미정 |
| 배포·상업 이용 라이선스 | 미정, 모델 카드 확인 |
| 한국어·제품 모델명·오류 코드 성능 | 평가 후 기록 |
| 출력 차원·정규화·거리 함수 | 미정 |
| query/document prefix·최대 토큰 | 모델 지침 확인 |
| CPU RAM·GPU VRAM·처리량 | 실측 |
| 추론 서버·버전·API 형식 | 미정 |

1024차원이라는 이유만으로 모델을 선택하지 않는다. 차원이 같아도 모델이 다르면 기존 벡터와 비교할 수 없다.

## 2. provider 분리 구현

향후 공통 인터페이스 예시:

```text
EmbeddingProvider
  embedDocuments(texts[]) -> vectors[]
  embedQuery(question) -> vector
  metadata() -> modelId, revision, dimension, preprocessingVersion
```

문서와 질문 prefix가 다른 모델을 지원해야 한다. 환경변수 후보는 아래와 같지만 **아직 구현되지 않은 새 설정**이다.

```text
EMBEDDING_PROVIDER=local
EMBEDDING_BASE_URL=<INTERNAL_MODEL_ENDPOINT>
EMBEDDING_MODEL=<MODEL_ID>
EMBEDDING_DIMENSIONS=<VERIFIED_DIMENSION>
EMBEDDING_TIMEOUT_MS=<TIMEOUT>
```

구현할 동작:

1. provider를 명시적으로 선택하고 누락된 설정은 시작 시 검증.
2. timeout·batch size·동시 실행 수·재시도 횟수 제한.
3. 응답 벡터 개수·길이·finite 숫자 여부 검증.
4. local-only 환경에서 OpenAI로 자동 폴백하지 않음.
5. 로컬 모델 장애 시 키워드 폴백 여부를 명시하고 로그·지표로 확인 가능.
6. 로컬 OpenAI 호환 서버를 쓰더라도 dimensions 필드 등 실제 호환성을 확인.
7. 검색 query와 적재 document가 같은 모델 revision·전처리 버전을 사용하는지 검증.

## 3. 스키마 전환 전략

기존 벡터를 새 모델 이름만 바꾸어 재사용하지 않는다. 권장 전환은 새 벡터 저장소/컬럼을 병행하는 방식이다.

1. 현재 DB 백업과 복원 검증.
2. 새 migration 파일로 모델 메타데이터·새 dimension의 컬럼 또는 테이블 추가.
3. 새 모델에 맞는 인덱스·검색 함수 추가. 큰 테이블의 인덱스 생성 시간·메모리 확인.
4. 기존 서비스는 기존 검색 경로 유지.
5. 신규 worker가 모든 허용 청크를 새 모델로 임베딩.
6. 누락·실패 건수 확인, 한국어 질문 평가.
7. query provider와 DB 검색 경로를 함께 전환.
8. 문제 시 이전 모델·검색 경로로 복귀.
9. 안정화 후 별도 변경으로 옛 컬럼·인덱스 정리.

소량의 실습 DB라 재생성이 쉬워도 원문·권한 근거는 보존한다. 이전 벡터 삭제 전에 새 모델을 검증한다.

## 4. 데이터 준비

설명서 수집은 저장소의 권한 게이트를 유지한다.

- 샘플·자체 작성·명시적으로 제공받은 텍스트로 시작.
- 외부 사이트 full text는 allowed/licensed 등 근거가 확인된 범위만 적재.
- PDF 원본 파일·hash·출처·revision을 기록.
- PDF 추출 worker에는 `pdftotext` 설치. API 이미지에 불필요한 수집 도구를 모두 넣지 않음.
- 로컬 파일 경로를 가리키는 PDF는 VM/worker에서 실제 접근 가능해야 함.
- 원본 PDF 저장 위치와 DB 백업은 별도 관리. DB dump만으로 파일이 복구되지 않음.

실습 명령은 맥북의 로컬 개발 DB에서 현재 구현된 importer 기준이다. 운영 적재는 맥북에서 미리 빌드한 importer/worker 이미지를 그램의 Job으로 실행한다. 그램에 Node 개발 환경을 설치하지 않는다.

```bash
npm run import:manual-text -- --file=backend/examples/manual-text.sample.json
npm run embed:manual-chunks -- --dry-run
```

로컬 provider를 구현하기 전 실제 embed 명령을 실행하면 현재 OpenAI 경로를 사용하므로 실행하지 않는다. 로컬 전용 egress 제한을 적용해 의도치 않은 외부 호출이 없는지도 검증한다.

## 5. 평가 데이터셋

최소 다음 유형을 포함하는 질문·정답 근거 표를 직접 만든다.

- 한국어 자연어 질문
- 제조사·모델명·오류 코드의 정확 일치
- 띄어쓰기·오타·유사 제품명
- 특정 revision에만 있는 절차
- 위험 경고가 포함된 설명서 구간
- 근거 없는 질문·다른 제품 질문

각 행에 질문, 기대 manual/revision/page, 실제 상위 근거, 순위, 응답 시간, 통과 여부를 남긴다. 키워드만/벡터만/혼합 검색을 비교한다. API 200만으로 품질 검증을 끝내지 않는다.

## 6. 운영 배치

모델 서버는 ClusterIP 또는 내부 LAN만 사용한다. 외부에서 임의 프롬프트나 대량 임베딩을 요청하지 못하게 한다. health/startup probe는 모델 로딩 시간을 고려한다. CPU/GPU resource 정책과 API batch 동시성을 맞춘다.

- 모델 weight는 라이선스·hash와 함께 로컬 보관.
- 모델 파일 PVC와 DB PVC를 구분.
- 이미 다운로드한 모델로 외부망 없이 재시작 가능한지 확인.
- worker는 Job으로 한 번 실행하는 것부터 시작.
- 실패 청크는 성공 처리하지 않고 재시도 가능 상태로 보존.
- 긴 PDF 적재가 사용자의 실시간 질문 응답을 잠식하지 않게 실행 시간·자원 분리.

## 7. 로컬 생성 LLM은 추가 단계

사용자가 요구하는 것이 '근거 검색'인지 '설명서 기반 생성 답변'인지 확인 후 추가한다. 모델 크기·양자화·KV cache·컨텍스트 길이에 따른 자원 실측이 필요하다. 근거 없는 답변 거부·출처 표시·모델 장애 폴백·입력 제한을 포함해야 한다. 답변 생성이 실패해도 원문 근거를 볼 수 있게 한다.
