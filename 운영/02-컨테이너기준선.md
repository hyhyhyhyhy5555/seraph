# 02. Kubernetes 이전 컨테이너 기준선

## 목적

앱 자체 문제와 Kubernetes 문제를 구분하기 위해 먼저 맥북에서 현재 Docker Compose 구성을 검증한다. 이 문서의 Compose·npm·importer·빌드 명령은 맥북 개발 환경에서만 실행한다. 그램 배포 검증은 03~04 문서에서 이미 빌드된 이미지로 수행한다. 이 단계는 LAN 전용 실습이며 인터넷에 DB나 개발용 API를 공개하지 않는다.

## 1. 도구 설치와 소스 준비

맥북 CPU·macOS에 맞는 로컬 Docker 런타임과 CLI·Buildx·Compose를 준비한다. 선택한 도구의 지원 조건을 확인하고 버전·출처를 기록한다. Docker Desktop을 선택하면 로컬 Linux VM을 통해 컨테이너가 실행된다. 그램에는 빌드용 Docker 환경을 만들지 않는다.

```bash
docker version
docker compose version
```

맥북에서 컨테이너 런타임이 실행 중인지와 Docker context를 확인한다. Ubuntu docker 그룹 권한 설정을 macOS에 그대로 적용하지 않는다.

보유 맥북의 소스 작업 디렉터리를 사용한다. 자체 Git 구축 후 remote를 연결하며, secret과 node_modules는 저장소에 추가하지 않는다. 명령은 맥북의 저장소 루트에서 실행한다.

```bash
git status --short
cat .nvmrc
cat .env.example
```

Node 설치는 실행 시 지원 중인 도구를 사용하되 `.nvmrc`와 호환성을 맞춘다. Node 버전을 변경할 경우 개발·CI·Dockerfile을 함께 맞추는 별도 변경으로 처리한다.

```bash
npm ci
npm run check
npm run build
npm run audit:prod
```

## 2. 현재 Compose의 제약 이해

`docker-compose.yml`은 개발용 DB 이름·사용자·비밀번호가 seraph이고 5432와 4000을 호스트에 공개한다. 그대로 인터넷 운영에 사용하지 않는다. 최초 DB 생성 때만 `db/migrations`를 initdb 디렉터리에서 실행한다.

이 단계에서는 맥북 방화벽·컨테이너 런타임·LAN 격리 설정을 확인하고 인터넷에서 개발 포트에 접근하지 못하게 한다. 가능하면 별도 Compose 실습 override에서 DB 바인딩을 127.0.0.1로 제한한다. Compose ports 배열은 단순 override에서 예상과 다르게 병합될 수 있으므로 `docker compose config`로 실제 결과를 확인한다. 실제 port binding 결과를 확인한다. Ubuntu의 UFW 절차를 맥북에 그대로 적용하지 않는다.

## 3. 실행과 기본 검사

```bash
docker compose config
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 backend
docker compose logs --tail=100 postgres
curl --fail http://127.0.0.1:4000/live
curl --fail http://127.0.0.1:4000/health
curl --fail http://127.0.0.1:4000/api/categories
```

`docker compose config` 결과에는 환경변수로 해석된 비밀값이 나올 수 있다. 화면 공유·작업 기록에 전체 출력을 복사하지 않는다.

기대 결과:

- postgres가 healthy, backend가 실행 상태다.
- `/live`는 ok true를 반환한다.
- `/health`는 db up을 반환한다.
- 카테고리 API가 JSON을 반환한다.

## 4. 실제 기능 확인

```bash
curl --fail http://127.0.0.1:4000/api/manuals
curl --fail -X POST http://127.0.0.1:4000/api/chat/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"세탁기 오류를 확인하는 방법"}'
```

응답 성공과 검색 품질은 다르다. 샘플 데이터에 질문에 대한 근거가 없으면 빈 근거나 안내 답변일 수 있다. 이 단계에서는 외부 OpenAI 키를 넣지 않고 키워드 경로로도 API가 작동하는지 확인한다.

권한 있는 샘플 본문은 `backend/examples/manual-text.sample.json` 내용을 검토한 뒤 importer로 적재한다. host에서 importer를 실행할 경우 DB 주소는 localhost이고, 컨테이너 안에서는 Compose service명 postgres다. 두 주소를 혼동하지 않는다.

```bash
npm run import:manual-text -- --file=backend/examples/manual-text.sample.json
```

이 명령은 host Node와 host용 DB 환경변수가 준비되어 있을 때 실행한다. `.env.example`을 참고해 별도 `.env`에 설정하고 커밋하지 않는다. 기존 운영 DB에 샘플을 무작정 넣지 않는다.

## 5. 모바일 LAN 연결

1. 휴대폰을 맥북과 접근 가능한 같은 LAN에 연결한다. 게스트 와이파이의 기기 격리를 확인한다.
2. 맥북에서 개발용 API가 4000 포트로 노출되는지 확인한다.
3. 휴대폰 브라우저로 `http://<MACBOOK_LAN_IP>:4000/live`를 열어 개발 네트워크를 먼저 검증한다.
4. 개발 앱 빌드에 `EXPO_PUBLIC_API_URL=http://<MACBOOK_LAN_IP>:4000`을 설정한다. 이 주소는 개발용이다.
5. Metro 프로세스를 재시작하고 필요한 경우 캐시를 정리한다.
6. 네이티브 HTTP 정책에 막히면 임시 개발 환경의 허용 범위를 확인한다. 출시 앱은 HTTPS로 전환한다.

공유기 포트 전달은 아직 하지 않는다. 실제 스토어 앱에서는 LAN 주소와 localhost를 사용하지 않는다.

## 6. 영속성 검증

변경 전후 카테고리·설명서 수를 기록하고 다음을 실행한다.

```bash
docker compose restart
curl --fail http://127.0.0.1:4000/health
docker compose down
docker compose up -d
```

다시 데이터 수가 같은지 확인한다. `down`은 기본적으로 named volume을 삭제하지 않지만 `down -v`는 삭제한다. 운영에서 `-v`로 초기화하지 않는다. 마이그레이션 SQL을 추가해도 기존 볼륨에 자동 적용되지 않는다는 점을 확인한다.

## 문제 해결 순서

1. DB 로그에서 초기화 SQL 실패 여부를 확인한다.
2. API 로그에서 DATABASE_URL·CORS 설정 오류를 확인한다.
3. pgvector 이미지와 PostgreSQL major가 맞는지 확인한다.
4. 맥북의 host 포트 충돌을 `lsof -nP -iTCP:4000 -sTCP:LISTEN`으로 확인한다.
5. 컨테이너 내부 연결 성공 후 host, LAN 순서로 넓힌다.
6. 실패 원인을 찾기 전 volume을 지우지 않는다.
