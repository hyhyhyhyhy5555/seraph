# 08. 공개 전 보안, 모니터링, 백업

## 목표

외부 요청으로 관리 데이터가 변조되지 않고, 장애를 발견하며, DB·파일·소스·서명키를 복구할 수 있게 한다. 구현 전인 항목은 완료 체크하지 않는다.

## 1. API별 공개 정책

`backend/src/server.ts`에서 모든 route를 목록화한다. 현재 API에는 외부 소스 권한 변경·작업 이력·문의·세션 등이 포함되어 있으므로 일괄 공개하지 않는다.

| 유형 | 정책 초안 |
| --- | --- |
| 카테고리·공개 설명서 검색 | 읽기 공개, pagination·입력 상한 |
| 설명서 질문·검색 | 요청 크기·빈도·실행 시간 제한 |
| 문의·설명서 요청 | spam 방지·입력 검증·보관 기간 |
| 세션 생성·메시지 조회/쓰기 | 세션 소유권·접근 토큰 검증 |
| 출처 권한 PATCH·수집 관리 | 관리자 인증·권한·감사 로그 |
| health 상세 오류 | 외부 응답 최소화, 상세 내용은 내부 로그 |

CORS는 브라우저 origin 정책이며 curl이나 악의적 앱의 요청을 막지 못한다. 세션 ID를 안다고 다른 사람의 대화를 조회할 수 없는지 반드시 확인한다. 앱에 공통 관리자 API key를 넣는 방식도 사용하지 않는다. EXPO_PUBLIC_*는 앱 사용자에게 노출되는 값이다.

## 2. 구현할 API 방어

1. 관리자 인증과 route별 권한 검사, 관리 UI/경로는 LAN·VPN 우선.
2. 세션 접근 정책 구현. 익명 앱이면 추측 불가능한 소유 토큰 등 별도 설계.
3. IP/사용자 단위 요청 제한, 질문 길이·검색 limit·batch 상한.
4. DB statement timeout, 외부/모델 호출 timeout, 연결 pool 상한.
5. SQL parameter binding과 Zod 입력 검증 범위 점검.
6. 운영 오류 응답에서 stack·DB 연결 정보 제거.
7. request ID와 구조화 로그, 비밀번호·토큰·질문 원문 기본 마스킹.
8. 신뢰 프록시 설정과 X-Forwarded-For 위조 방지.
9. dependency·container 취약점 검사 결과 처리.
10. 앱에서 인증서 검증을 끄지 않음.

## 3. Kubernetes와 호스트

- 관리자 kubeconfig·SSH private key는 관리 장비에만 보관.
- service account 자동 mount 불필요하면 끔.
- 컨테이너 non-root, capabilities drop, privilege escalation 금지.
- 검증 가능한 범위에서 readOnlyRootFilesystem과 필요한 writable volume만 허용.
- namespace 간 접근 제한. NetworkPolicy 적용 후 DNS·DB·모델·필요 egress만 허용.
- 로컬 AI 환경의 API가 외부 AI endpoint를 호출하지 못하는지 확인.
- DB는 API·migration·백업 작업만 접근 가능하게 제한.
- CPU·RAM limit, 디스크·로그 용량 제한.
- K3s Secret 암호화 설정 시 기존 secret 재암호화와 복구키 절차도 준비.
- OS·K3s·DB 패치 날짜와 되돌림 계획 기록.

정책을 적용한 후 실제 차단/허용 테스트를 한다. NetworkPolicy YAML이 있다는 사실만으로 enforcement를 가정하지 않는다.

## 4. 모니터링 도입 순서

확인된 RAM 16GB·여유 저장 공간 약 39GB를 고려해, 공간 확보 후에도 무거운 전체 스택을 처음부터 강제하지 않는다.

1. 초기: `kubectl get`, journalctl, 컨테이너 stdout·디스크 확인.
2. 다음: Prometheus 계열 수집·Grafana 대시보드, 보관 기간·PVC 제한.
3. 필요 시: 중앙 로그 수집, 민감정보 마스킹·보관 기간.
4. LAN 외부의 휴대폰 또는 별도 장비에서 가용성 확인.

동일 PC의 모니터링은 PC 전체가 꺼지면 알림도 보낼 수 없다. 별도 장비·외부 확인 수단이 없으면 이 한계를 기록한다. 이메일/메신저 알림 채널은 사용자 선택 후 연결하며 현재 문서 작성으로 알림을 발송하지 않는다.

## 5. 최소 지표·경보

| 지표 | 초안 기준 | 대응 |
| --- | --- | --- |
| 외부 API | 연속 실패 | 네트워크→Ingress→API 확인 |
| HTTP 5xx·지연 | 평소 기준보다 급증 | 최근 배포·DB·모델 확인 |
| Pod 재시작·OOM | 새 발생 | previous 로그·메모리 확인 |
| SSD·PVC | 여유 20% 경고, 10% 긴급 초안 | 이미지·로그·백업 정리 |
| TLS | 만료 30일 이내 초안 | 갱신 challenge 확인 |
| DB 백업 | 예정 실행 후 성공본 없음 | 즉시 수동 백업·원인 조사 |
| CI·Registry | 디스크 증가·실패 | cache·retention 확인 |
| DB·임베딩 | 대기·실패 누적 | worker·모델 상태 확인 |

임계값은 실측 후 변경한다. 경보마다 담당자·확인 순서·회복 조건을 기록한다.

## 6. 백업 대상

| 대상 | 백업 내용 | 복원 검증 |
| --- | --- | --- |
| PostgreSQL | pg_dump custom format + 역할/권한 재현 절차 | 새 DB restore·행 수·질문 |
| PDF·업로드 | 원본 파일·hash·경로 | 임의 샘플 열기·DB 참조 |
| Git | repos·LFS·Gitea DB·설정 | clone·commit·LFS 확인 |
| Registry | package 파일·메타데이터·설정 | digest pull 확인 |
| Kubernetes | 선언 파일·Secret 복구 자료·데이터스토어·token | 격리 VM 복구 |
| AI | 모델 revision·weight·라이선스·전처리 | 동일 출력 차원·질문 검색 |
| Android | upload keystore·alias·암호 | 서명 확인·다음 버전 업로드 |
| Apple | 인증서·private key·profile·복구 정보 | Archive 서명·계정 접근 |

같은 SSD의 다른 폴더·다른 VM·snapshot은 장비 고장 대비 백업이 아니다. 외장 디스크 또는 별도 물리 장치에 암호화 사본을 두고, 한 사본은 상시 연결하지 않는 방안을 검토한다. 암호화 복구키도 그 디스크 한 곳에만 저장하지 않는다.

## 7. PostgreSQL 백업 예시

초기 수동 백업은 private 관리 디렉터리에서 실행한다. 다음은 local socket 관리 권한이 준비된 경우의 예시다. 인증 방식은 실제 배포에 맞춘다. TTY 옵션 `-t`를 쓰지 않는다.

```bash
umask 077
backup_stamp=$(date -u +%Y%m%dT%H%M%SZ)
kubectl -n seraph-prod exec seraph-postgres-0 -- \
  pg_dump -U <BACKUP_USER> -d seraph -Fc > "<PRIVATE_BACKUP_DIR>/seraph-${backup_stamp}.dump"
```

종료 코드·파일 크기를 확인하고 `pg_restore --list`로 archive 목록을 검사한다. 이것만으로 복원 성공이 증명되지는 않는다. dump를 만들 때 중간 오류로 0 byte 파일이 생길 수 있으므로 실패본은 정상 보관 목록에서 제외한다.

실행 시각·커밋·migration 버전·DB major·이미지 digest·파일 hash를 별도 manifest에 기록한다. 파일은 암호화해 외부 저장 장치로 복사하고 hash를 비교한다. CronJob으로 바꾸면 실패 경보와 retention도 함께 구현한다.

초안 정책은 매일 백업, 주요 migration 직전 추가 백업이다. RPO(허용 데이터 손실 시간), RTO(복구 목표 시간)는 사용자 요구와 디스크 용량을 보고 확정한다. 일일 백업만 있으면 최악의 경우 하루 가까운 데이터가 손실될 수 있다.

## 8. 실제 DB 복원

1. 운영과 분리된 namespace·새 PVC·새 DB를 만든다.
2. PostgreSQL major와 pgvector 확장 버전을 맞춘다.
3. 필요한 role·extension을 준비한다.
4. dump를 대상 Pod로 전달하거나 stdin으로 pg_restore한다.
5. `pg_restore --exit-on-error` 결과 확인, 운영 DB로 향하지 않았는지 재확인.
6. 테이블 수·주요 행 수·manual revision·권한 이벤트·vector 차원 확인.
7. 복원한 API로 카테고리·질문·세션 시나리오 실행.
8. 복원 시간·실패 지점·백업 시점 이후 손실 범위 기록.

운영 PVC를 덮어쓰는 것은 첫 복원 실습 경로가 아니다.

## 9. K3s 데이터스토어 백업

기본 단일 K3s의 SQLite와 embedded etcd는 백업 방식이 다르다. 설치한 데이터스토어를 먼저 확인한다. etcd snapshot 명령을 SQLite에 사용하지 않는다. 데이터스토어 백업뿐 아니라 server token이 복원에 필요하다. Secret·token 포함 백업은 강하게 보호한다.

DB PVC 데이터와 Git/모델 파일은 K3s 데이터스토어 백업에 자동 포함되지 않는다. VM snapshot은 DB 일관성·물리 장애 복구를 대신하지 못한다.
