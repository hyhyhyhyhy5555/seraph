# 11. 출시 리허설과 장애 대응

## 목표

첫 출시 전, 앞으로 버전을 바꿀 때, 집 PC가 꺼졌을 때 무엇을 해야 하는지 재현 가능한 순서로 만든다. 배포 성공은 단순 rollout 완료가 아니라 실제 앱 기능·데이터·복구 경로까지 확인한 상태다.

## 1. 출시 전 리허설

staging에서 실제 운영과 같은 순서로 수행한다.

1. release commit·이미지 digest·DB migration 버전 고정.
2. 새 백업을 만들고 별도 DB로 복원 가능함 확인.
3. migration 수행 후 이전 API 버전도 작동하는지 확인.
4. 새 API를 같은 이미지 digest로 배포.
5. rollout·health·검색·질문·문의·세션 권한 확인.
6. Android release와 iOS TestFlight 설치본에서 외부망 테스트.
7. API 이미지를 이전 digest로 되돌려 호환성 확인.
8. 새 버전 재배포와 정상 상태 확인.
9. Windows 재부팅 후 VM→K3s→DB→API 순서로 복구 확인.
10. 결과·걸린 시간·남은 문제를 작업 기록에 작성.

## 2. 앱과 서버의 버전 순서

스토어 앱은 모든 사용자가 동시에 업데이트하지 않는다. 보통 서버에 호환 기능을 먼저 추가하고 앱을 출시한다. 구버전 앱도 계속 동작하는지 확인한다.

DB 변경은 expand → 새 코드 → 데이터 이행 → 관찰 → contract 순서를 기본으로 검토한다. 예를 들어 컬럼 이름 변경을 즉시 DROP/RENAME만으로 처리하면 구버전 API·앱이 깨질 수 있다. 파괴적 migration은 별도 점검 시간과 백업·복구 계획을 세운다.

API image rollback은 DB schema rollback이 아니다. DB를 과거 dump로 복원하면 이후 사용자의 문의·대화가 손실될 수 있으므로 단순한 배포 실패 때 먼저 이미지 rollback 또는 forward fix를 검토한다.

## 3. 실제 공개 당일

- [ ] 운영자 연락·지원 URL·개인정보처리방침 정상
- [ ] API·DB·TLS·공인 IP·디스크·백업 최신 상태
- [ ] 최근 정상 이미지와 서명 artifact 보존
- [ ] Windows 업데이트·예정 재부팅 확인
- [ ] 스토어 심사 승인·배포 국가·가격·출시 방식 확인
- [ ] 소규모 공개 또는 가능한 rollout 방식 선택
- [ ] 앱 설치·기능·오류율·문의 확인
- [ ] release 기록에 실제 공개 시각과 스토어 링크 기재

심사·공개 승격은 해당 시점 사용자의 출시 의사와 준비 상태에 맞춰 수행한다. 이 문서를 작성하는 작업은 스토어 제출이나 외부 메시지 발송을 포함하지 않는다.

## 4. 장애 확인 순서

```text
외부 LTE 접속
 → DNS·공인 IP
 → 공유기 80/443 전달
 → Windows 전원·VM 실행
 → Ubuntu 네트워크
 → K3s node·Ingress
 → API readiness·로그
 → DB·PVC·디스크
 → 모델 서버·검색 worker
```

한 번에 여러 설정을 바꾸지 않는다. 증상을 재현하고 마지막 변경을 기록한 뒤 한 항목씩 확인한다.

## 5. 기본 명령 모음

Ubuntu 관리 세션:

```bash
uptime
free -h
df -h
sudo systemctl status k3s --no-pager
kubectl get nodes -o wide
kubectl -n seraph-prod get pods,svc,ingress,pvc -o wide
kubectl -n seraph-prod get events --sort-by=.lastTimestamp
kubectl -n seraph-prod logs deployment/seraph-api --tail=100
kubectl -n seraph-prod logs deployment/seraph-api --previous --tail=100
kubectl -n seraph-prod rollout history deployment/seraph-api
```

`logs --previous`는 이전 종료 컨테이너가 있을 때만 동작한다. 일부 명령의 오류가 전체 장애 원인이라는 뜻은 아니다. 로그를 공유할 때 토큰·개인정보·DB 주소를 마스킹한다.

## 6. 장애별 절차

### A. Windows 재부팅·정전

1. 공유기 인터넷과 PC 부팅 확인.
2. VM 자동 시작·고정 IP 확인.
3. 시간 동기화·디스크 마운트 확인.
4. K3s·DB·API·모델 기동 상태 확인.
5. 외부 LTE에서 API와 앱 확인.
6. 비정상 DB 복구 로그와 데이터 일관성 확인.
7. 재발 방지: 자동 시작·전원 정책·UPS 도입 여부 기록.

### B. DNS·공인 IP 변경

1. 외부 DNS 결과와 현재 공인 IP 비교.
2. DDNS 작업·DNS API token·TTL 확인.
3. 잘못된 AAAA 레코드 확인.
4. 공유기 포트 전달 대상 IP가 바뀌지 않았는지 확인.
5. 외부와 내부를 나눠 테스트해 NAT loopback 문제 구분.

### C. 새 API 배포 실패

1. rollout 상태·events·현재/이전 컨테이너 로그 확인.
2. 이미지 pull·환경변수·DB migration 실패 구분.
3. 이전 이미지와 현재 DB 호환성 확인.
4. 선언 파일의 image를 이전 digest로 되돌려 적용.
5. rollout·실제 앱 확인.
6. 장애 이미지·로그는 조사용으로 보관하고 원인 수정 후 재배포.

빠른 수동 복구로 `kubectl rollout undo`를 사용할 수도 있지만, 선언 파일도 동일한 정상 상태로 갱신해야 다음 apply에서 실패 버전이 다시 적용되지 않는다.

### D. DB 접속 실패

1. DB Pod·PVC·디스크 용량 확인.
2. DB 로그에서 crash recovery·인증·연결 한도 확인.
3. API Secret·DNS·NetworkPolicy 확인.
4. 최근 migration과 권한 변경 확인.
5. 데이터 손상 의심 시 쓰기 유입을 제한하고 현 상태 사본 보존.
6. 별도 DB에 최신 백업 복원·검증 후 전환 계획 수립.

PVC 삭제·initdb 재실행으로 해결하지 않는다.

### E. 디스크 부족

1. OS·VM 가상 디스크·PVC·Registry 중 어느 곳인지 식별.
2. 최신 백업을 먼저 보존.
3. 오래된 빌드 cache·회전된 로그·보관 정책 초과 artifact부터 정리.
4. 운영/rollback 이미지와 DB 파일은 무작정 삭제하지 않음.
5. 증설 시 물리 디스크→가상 디스크→partition/filesystem→PVC 각 계층 확인.
6. reclaimPolicy·볼륨 확장 지원을 확인한 절차로 진행.

### F. AI 모델 중단

1. API 키워드 폴백 동작 확인.
2. 모델 Pod startup·메모리·weight 경로 확인.
3. worker 동시성·사용량을 줄이고 재기동.
4. query/document 모델 revision·dimension 일치 확인.
5. local-only 요구에 반해 외부 API를 임시 연결하지 않는다.

### G. 인증서 만료·갱신 실패

1. certificate·order·challenge 상태 확인.
2. DNS와 80 포트·ACME 경로 접근 확인.
3. issuer 계정·DNS token·clock 확인.
4. staging에서 원인 검증 후 production 발급.
5. 앱 TLS 검증을 끄는 업데이트로 우회하지 않음.

## 7. 전체 호스트 손실 복구 순서

1. 복구할 물리 PC/디스크·백업 장치 준비.
2. Windows 가상화·LAN·Ubuntu VM 재구성.
3. 자체 Git·Registry 또는 오프라인 복구 이미지 확보.
4. 동일/호환 K3s와 StorageClass 준비.
5. Secret·token을 보호된 경로로 복구.
6. DB·원본 PDF·모델 파일 복원.
7. 고정된 API image·설정 배포.
8. LAN 검증 후 도메인·HTTPS 외부 연결.
9. Android·iOS 스토어 설치본으로 확인.
10. 손실 데이터 범위·실제 복구 시간 기록.

## 8. 운영 주기

| 주기 | 작업 |
| --- | --- |
| 배포마다 | 검사·백업·migration·rollout·기능·롤백 경로 |
| 매일 | 서비스·디스크·백업 성공·worker 실패 |
| 매주 | 에러·로그·취약점·용량 추세·키 만료 |
| 매월 초안 | 별도 DB 복원 실습·OS/K3s 패치 검토 |
| 인증서/계정 변경 시 | 복구 정보·runner·권한·기기 검증 |

## 종료 기준

양쪽 스토어 공개만으로 실습을 끝내지 않는다. 다음 업데이트 배포, 이미지 rollback, DB restore, 호스트 reboot를 각각 한 번 이상 재현하고 증적을 남긴다.
